# Матрицы прав в рабочих пространствах (COREDEV-610)

Задача: https://citeck.ecos24.ru/v2/dashboard?ws=COREDEV&recordRef=emodel/ept-issue@COREDEV-610

Матрица `emodel/perms` принадлежит тому же пространству, что и её `typeRef`.
Это сохраняет существующее правило применения прав к типу и закрывает подмену
глобальных прав матрицей, задеплоенной из WS. Отдельных переопределений матрицы
глобального типа для конкретного WS нет.

## Хранение и доступ

- `TypePermsDef` сохраняет исходные четыре поля: `id`, `typeRef`, `permissions`,
  `attributes`. Пространство матрицы определяется по её типу; общего DTO и
  изменения версии `ecos-model-lib` для этого не требуется.
- Колонка `type_permissions.workspace` содержит локальный ID WS, вычисленный
  backend из типа при сохранении. Глобальная область хранится как пустая строка.
  Колонка нужна для выборок, индексов и уникальности; клиент не задаёт её значением
  DTO. Records-атрибуты `workspace`, `workspaceRef` и `_workspace` вычисляются по типу.
- ID матрицы в DTO локальный; ссылка Records API имеет вид
  `emodel/perms@<wsSystemId>:<id>`. Ключ уникальности: `(workspace, ext_id)`.
- Поиск по типу использует `(workspace, type_ref)`, причём пространство определяется
  из ссылки типа. Namespace в ID типа (`namespace:contract`) не меняет его
  пространство; новая матрица такого типа получает UUID. Одинаковые локальные
  ID типов и матриц в разных WS независимы.
- Глобальные матрицы изменяют только ADMIN/SYSTEM. Матрицы WS также изменяют
  менеджеры этого WS и его системная учётная запись. Участник без роли менеджера
  не может создавать, изменять или удалять матрицы.
- При обычном сохранении через Records полный `typeRef` определяет WS независимо
  от страницы. Проверка прав выполняется в пространстве типа; администратор может
  создать глобальную матрицу со страницы WS, менеджер WS не получает права на
  глобальный или чужой тип. Префикс ссылки матрицы должен совпадать с WS типа.
  При изменении проверяются права на исходную запись и новый тип; исходная
  ссылка не позволяет незаметно сменить WS. При деплое ecos-app отдельно
  проверяется совпадение пространства типа с целевым WS, включая SYSTEM.
- `_workspace` при мутации принимает локальный ID или ссылку `emodel/workspace@...`
  и используется для разрешения `CURRENT_WS` при создании/копировании переносимой
  матрицы. Полный `typeRef` при создании не зависит от контекста страницы, даже
  если общий `Records.save()` автоматически его подставил. Для существующей
  матрицы `CURRENT_WS` связывается с её исходным WS.
- Журнальные выборки и их `totalCount` учитывают доступные и запрошенные пространства.
  Прямое чтение матрицы WS доступно участникам этого WS, ADMIN/SYSTEM и WS-system.
  `permissions._has.Write?bool` отражает право изменять саму матрицу.

Наполнение общего реестра полностью контролирует emodel; остальные сервисы
читают опубликованные матрицы. Проверка применимости находится только в
`TypePermsService`: одна проверка используется для начальной выборки и для
снимков `before`/`after` перед публикацией через `TypePermsInitializer`.
Некорректные старые записи остаются доступны для исправления и удаления в БД,
но не публикуются в registry. Их удаление не публикует событие для матрицы,
которая туда не попадала; исправление публикует уже корректное значение.

`TypePermissionsRegistry` в `ecos-webapp-commons` поддерживает индекс по типу
без повторной проверки пространства, ID или ссылки типа и без зависимости от
`WorkspaceService`. При смене типа и удалении матрицы предыдущий ключ поиска
освобождается. Контракт предполагает, что все значения публикует emodel;
произвольное некорректное наполнение registry извне не поддерживается.

## Структурированные идентификаторы

Как у типов и шаблонов нумерации, внутренние операции матриц используют
`IdInWs`: `getPermsById`, `getRecordDataById`, `getPermsMeta` и `delete` принимают
структурированный ID. `getId(def)` возвращает локальный ID вместе с пространством
типа, а серверный снимок хранит исходный `IdInWs` записи, в том числе для
некорректных старых строк. Сохранение и выбор строки БД работают с этой парой.
Глобальные алиасы вроде `default` приводятся к пустой области хранения.

Records преобразует строковую ссылку в `IdInWs` на входе и обратно на выходе;
initializer выполняет обратное преобразование только при публикации ключа registry.
Удаление артефакта передаёт `IdInWs.create(workspace, artifactId)` непосредственно
сервису, без преобразования в строку и повторного разбора. Новый префиксованный
Records reference также ограничивает пространство создаваемой матрицы.

Новый локальный ID матрицы не может содержать `:`. Ограничение относится только
к матрицам: WS-префикс транспортной ссылки и namespace в ID типа допустимы.
Поле `id` DTO/артефакта локальное: значение `ws:id` в нём также отклоняется,
а WS-префикс разбирается на границе ссылки Records.
При пустом ID существующая матрица сохраняет прежний ID. Новая матрица обычного
типа получает его локальный ID; если ID типа содержит `:`, матрица получает UUID.
Явный ID с `:` отклоняется при создании и переименовании через сервис, Records
и eapps. ID других артефактов этим правилом не ограничиваются.

Существующие матрицы с `:` остаются применимыми, доступными для чтения, изменения,
JSON roundtrip, экспорта и удаления. Они автоматически не переименовываются.
Для создания копии такой матрицы в другом WS нужно задать новый локальный ID
без `:`. Общий DTO остаётся четырёхпольным; пространство не добавляется в JSON,
а `CURRENT_WS` и проверка цели деплоя остаются прежними.

## Артефакты и админка

`model/permissions` обрабатывается через `WsAwareArtifactHandler`. Пространство
задаёт цель деплоя; ссылки `CURRENT_WS:` и типы из того же пакета артефактов
привязываются к этому WS. Деплой матрицы на чужой или глобальный тип отклоняется.

При экспорте ID матрицы остаётся локальным, `workspace` опускается, а префикс
ссылки своего типа заменяется на `CURRENT_WS:`. Экспорт можно импортировать
в другое пространство вместе с его типом. Удаление артефакта учитывает WS.
Records API (`?json` / `_self?json`) возвращает исходный DTO с четырьмя полями.
Поля `workspace` в нём нет. При сохранении JSON существующей матрицы `CURRENT_WS`
разрешается в контексте исходной записи; отдельные атрибуты `workspace?str` и
`workspaceRef?localId` вычисляются по её типу.

Пункт «Матрицы прав» / «Permission matrices» добавлен в существующий патч
`add-emodel-admin-journals-to-ws-menu`, рядом с типами и шаблонами нумерации.
Используется журнал `uiserv/journal@type-perms`. Аналогия с действиями COREDEV-490
сохранена; изменять собственный патч меню uiserv для этого не требуется.

## Существующие данные

Liquibase добавляет пространство и меняет уникальность ID. Перед заполнением
реестра `TypePermsInitializer` переносит старые записи:

1. Пространство из префикса ID матрицы имеет приоритет.
2. Для непрефиксованного старого ID пространство определяется по ссылке типа.
3. Префиксованный ID разделяется на пространство и локальный ID.
4. При совпадении локальных ID разных типов обе матрицы сохраняются: конфликтующий
   ID получает суффикс `-legacy-<databaseId>`; изменение записывается в лог.
5. Дубликаты матрицы одного типа в одном WS, как и раньше, сокращаются до последней
   изменённой записи.

Старые матрицы с несовпадающим пространством типа остаются в БД для исправления
или удаления через журнал, но не попадают в рабочий реестр и поиск прав типа.
Внутренний серверный `TypePermsRecordData` хранит снимок записи с полным
`IdInWs` из БД и метаданными, отдельно от общего DTO. Поэтому некорректная старая
матрица остаётся доступна по прежней ссылке WS и не становится глобальной из-за
пространства своего ошибочного типа. Исправление/удаление такой записи не
затрагивает действующую глобальную матрицу с тем же ID.
Если старая ошибка уже перезаписала единственную глобальную запись и сведения
о её происхождении потеряны, восстановить прежнее содержимое автоматически нельзя.
